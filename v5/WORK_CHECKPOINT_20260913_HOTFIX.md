# 2026-09-13 v5.2.4 긴급 수정 보고

기준: 게시된 v5.2.3 `f519ca2`에 대한 사용자 실사용 회귀 보고.
요청 범위는 ZERO 인식/온도 유실과 Sync 첫 전송 실패를 수정하고 긴급 릴리스하는 것이다.

## 확인한 원인

1. MAIN의 `loop()`는 시작 시각 `now`를 보관하지만 5.2.3의 새
   `serviceCompanion(millis())`와 업로드 콜백은 그 뒤의 시각으로
   `lastValidLinkMs`를 갱신한다. 루프 끝에서 이전 `now`에서 최신 수신 시각을
   빼면 unsigned 정수 차이가 약 49일로 나타나 5초 만료 조건을 즉시 만족한다.
   예: 루프 15,000 ms, 정상 응답 15,009 ms → 4,294,967,287 ms.
   이때 링크 시각, 협상 버전, ZERO 기능 정보를 지우므로 정상 배선에서도
   온도/온라인 정보가 사라지고 HELLO가 반복된다. 부하·화면 갱신·콜백 시점에
   따라 발동하므로 특정 IDLE 정책이 보드 간 SPI를 끊는 현상처럼 보일 수 있다.
2. OTA 완료 후 `StabilityHold`는 실제 무응답이면 10분 관찰 시간을 다시 센다.
   1번 오류 때문에 이 대기가 반복될 수 있다. 포털은 관찰 대기를 포함한
   `bundleUpdate.active()` 전체를 Sync 업로드 금지로 사용하고 있었다.
3. 첫 256 KiB 묶음의 raw 업로드가 거절되면 본문 도중 클라이언트를 닫아
   정상 오류 응답을 주지 못했다. Safari의 `Load Failed`는 그 경로와 일치한다.
   화면의 약 0.2 MiB는 브라우저 변환량이므로 SD에 그만큼 기록됐다는 뜻은 아니다.

이는 소스와 호스트 재현으로 확인한 결함이다. 사용자 기기의 UART/HTTP 캡처를
확보한 것은 아니므로 모든 하드웨어 통신 실패를 이 원인 하나로 확정하지 않는다.

## 수정

- 정상 응답 승인 시 현재 시각을 기록하고, MAIN은 link/HTTP 콜백 이후와
  최종 TFT flush 이후에 시각을 다시 읽는다. 상태 표시와 연결 만료 계산에
  최신 시각을 사용한다. 실제 5초 무응답·CRC·ACK·재협상 조건은 유지한다.
- `blocksMediaUpload()`는 관찰 대기만 제외한다. 실제 설치 및 서명된 펌웨어
  SD 보관 작업은 계속 배타적이며 다른 OTA 작업의 `active()` 의미는 바꾸지 않는다.
- 신규 raw 및 기존 multipart Sync 경로에 같은 관찰 대기 예외를 적용한다.
- 최대 320 KiB의 올바른 요청은 작업 충돌·저장 위치 불일치·SD 기록 오류가
  발생해도 제한된 본문을 마저 소비한 뒤 HTTP 409와 이유를 반환한다.
  잘못된 메타데이터/형식/과대 요청, 사용자 취소·열 보호는 즉시 중단한다.
- Sync 상태 API의 `upload_allowed`/`upload_error`로 변환 전에 수신 가능 상태를
  확인한다. 전송 시작 전 거절은 기존 임시 미디어를 삭제하지 않는다.
- 256 KiB 묶음, 8 KiB PSRAM 기록 버퍼, 부분 전송 재개, 전체 MVJ1 CRC/JPEG
  검사·인덱스 확정·오디오 시간 기준 재생을 유지한다.
- Wi-Fi 아이콘, 12개 정보 페이지, 독립 LED, NOW 전용 BLE 정책 및 ZERO
  펌웨어 동작 로직은 유지한다. MAIN/ZERO/SAFE의 배포 버전만 함께 5.2.4로 올린다.

## 재현 및 검증

- 수정 전 실제 MAIN 루프 끝 부분을 실행한 검사에서 `lastValidLinkMs`가
  정상 수신 직후 0이 되어 실패했다. 실제 Sync raw 콜백과 SD 수신 클래스를
  실행한 검사도 관찰 대기의 첫 256 KiB 요청을 거절하여 실패했다.
- `tests/extract_v5_runtime_fixtures.py`는 검사 시점의 실제 소스 블록을 추출한다.
  별도로 복제한 만료/HTTP 구현을 시험하지 않는다. 전체 Arduino 런타임과
  실제 TCP 소켓·SPI 전기 신호는 호스트 검사 범위에 포함되지 않는다.
- MAIN 검사: 루프보다 늦은 ACK, HTTP 콜백 후 시각, 1,000회 유휴 수신,
  실제 5초 무응답, millis wrap 전후를 검사한다.
- Sync 검사: 관찰 대기의 첫 256 KiB 업로드, 실제 설치/다운로드 충돌,
  부분 12,345바이트 중단과 후속 재개, offset 불일치, SD 기록 실패,
  과대 요청, 1 MiB 이상 파일의 전체 수신 및 90,000프레임 CRC/JPEG 인덱스 확정.
- 기존 bundle 검사는 실제 설치/관찰 단계의 미디어 차단 경계를 확인한다.
  브라우저 검사는 변환 전 거절과 기존 1,200프레임 전송·응답 유실 재개를 확인한다.

검증 완료:

- `./tools/test-core.sh` 통과 (v3 회귀·문서/버전·공식 릴리스 도구 계약 포함).
- `./tools/test-v5.sh` 통과 후 추가한 1 MiB/변환 전 검사까지
  `ASAN_OPTIONS=detect_leaks=0 V5_SANITIZE=1 ./tools/test-v5.sh` 통과.
- 새 MAIN 시각 검사와 실제 raw 콜백/SD 수신 검사, 기존 HTTP·SPI·버튼·BLE
  역할·bundle/SAFE·미디어 검사를 함께 실행했다. LeakSanitizer는 환경 제약으로
  비활성화했고 AddressSanitizer/UndefinedBehaviorSanitizer는 활성화했다.

정식 릴리스는 제품키 MAIN/ZERO/SAFE 빌드, 13개 자산의 서명·SHA·고정 offset,
원자적 main/tag push와 게시 후 전 자산 재다운로드 검증을 수행한다.

## 적용 후 실기 확인

- 5.2.4 MAIN/ZERO 설치 및 ZERO 재부팅 검증 후 CORE에서 온도/링크 유지.
- CORE 유휴·화면 꺼짐·NOW 전환·AP 진입 후 실제 BLE/링크 동작 확인.
- OTA 관찰 대기 중 Sync 저장을 시작해 0.2 MiB를 넘기고 전체 검증/재생 확인.
- 실제 SD/전파 환경 및 휴대폰에서 취소·재접속·장시간 상태를 확인해야 한다.
  이 작업은 기기에 유선 기록하거나 관리자 Stable 버전을 변경하지 않는다.
