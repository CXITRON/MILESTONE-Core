# v5.2.5 캐시 검사 지연 수정

## 확인한 사실

- 사용자는 5.2.4에서 프로필 전환·NOW 시작·업데이트 확인 시 10초 이상
  지속되는 심한 지연과 CORE 초 표시 건너뜀/깨짐을 보고했다. ZERO 링크
  회귀 수정은 정상 작동한다고 확인했다.
- MAIN/ZERO USB 로그에서 5.2.4와 CRC 오류 없는 링크를 확인했다. 자동
  업데이트 확인은 MAIN의 Wi-Fi/NTP 준비 시간 초과로 종료된 사례가 있었다.
- 정식 5.2.4 BIN과 SHA-256이 동일한 빌드를 만들어 USB JTAG로 확인했다.
  명시적으로 CPU를 재개한 8회 표본 모두 MAIN의 V5Artwork::maintain에서
  SD 폴더의 파일/마커를 조회하는 경로였다. CORE에서도 이 경로가 실행됐다.
  캐시에 이미지 66개가 있었고 한 파일마다 fopen/stat 및 폴더 재검색이 반복됐다.
- USB 송신 timeout은 두 보드 모두 0이었다. 로그 수신을 중지한 상태에서도
  위 SD 경로를 확인했으므로 로그 송신을 주원인으로 단정할 근거는 없다.
- 초기 디버거 연결 해제 시 CPU가 자동 재개되지 않아 정지 시간이 누적
  지표에 포함됐다. 이후 명시적 재개와 지표 초기화로 구분했다. 새 지표에서
  MAIN 루프 최대 3,379ms, TFT flush 최대 3,110us를 읽었지만 최초 측정의
  약 0.8초 정지 영향은 남을 수 있다. 이를 순수 실시간 지연 실측으로
  주장하지 않는다. 두 보드는 재개했고 디버거는 종료했다.

## 수정 범위

- CORE에서 캐시 목록 검사를 수행하지 않는다. NOW는 메타데이터 준비와
  곡 변경 안정화 이후, 설정 포털은 허용되는 유휴 구간에만 검사한다.
- 메뉴·버튼 조작 직후·업데이트 확인·MEDIA의 전송/재생을 우선한다.
  보류된 검사는 커서를 유지하여 처음부터 다시 읽지 않는다.
- 매 60초 전체 검사를 없애고 초기 집계/실제 캐시 변경/명시적 재집계로
  한정한다. getNextFileName으로 파일을 열지 않고 이름을 순회하며,
  각 파일의 정보·중복·custom·blocked·use 조회를 루프별로 나눈다.
- stat 한 번으로 필요한 정보만 읽어 File/exists의 중복 열기를 피한다.
  조회 오류는 없는 파일로 처리하지 않고 이전 인덱스와 파일을 보존한다.
- 캐시 집계 대기 중 반복 저장 시도의 불필요한 파일 조회와 이미 저장된
  커버의 검사 종료 시 재검증을 제거한다. 신규 커버의 CRC·저장 후 재검증,
  임시 파일 복구, 2GiB 한도와 custom 보호, 인덱스 A/B 게시 순서는 유지한다.
- ZERO BLE 구현, SPI 배선/클럭, TFT 렌더러, OTA 서명·설치 순서,
  NVS 스키마, Sync 전송 형식은 변경하지 않는다.

## 검증 범위

- 기존 캐시 저장/재시도/임시 파일 복구/custom 보호/용량 제한 및 Sync
  회귀 검사에 더해 80개 커버와 메타데이터·마커로 분할 검사를 검증한다.
  보류/재개, 루프당 메타데이터 조회 1회, 변경 없는 장시간 재검사 없음,
  I/O 오류 시 이전 목록 보존과 복구를 검사한다.
- 정식 milestone-release의 호스트 회귀 검사, MAIN/ZERO/SAFE 빌드,
  서명·13개 배포 자산 검증을 통과해야 게시한다.
- 사용자가 추가 실험보다 빠른 수정 릴리스를 요청하여 5.2.5의 유선 설치와
  장시간 실사용 검증은 수행하지 않았다. 화면 깨짐, NOW 연결, OTA 확인이
  모두 해결됐다고 단정하지 않는다. 이번 수정은 확인된 MAIN 캐시 검사
  병목을 대상으로 하며 SD 개별 I/O 자체의 최악 응답 시간까지 보장하지 않는다.
